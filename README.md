# 接口自动化测试框架 v1

> 基于 **Python + pytest + requests + YAML** 的接口自动化测试框架
> 被测对象：[JSONPlaceholder](https://jsonplaceholder.typicode.com)（公开 mock API，无需注册）
>
> **当前状态：31 条用例，28 通过 + 3 条标记为预期失败**（见「踩坑记录」与「落库校验」）

---

## 一、这个项目解决什么问题

手工用 Postman 点接口，每改一次代码就要重测一遍，几十个接口根本点不过来。
这个框架把接口用例**代码化**，做到：

- **一条命令跑完全部用例**：`pytest`
- **数据与代码分离**：改测试数据不用动 Python 代码（YAML 驱动）
- **失败时能直接定位**：断言失败会带上请求地址、状态码、响应体
- **能接进 CI**：代码提交自动跑（见「后续升级」）

---

## 二、技术选型与理由

| 选了 | 为什么不用别的 |
|---|---|
| **pytest** | 比 unittest 少写样板代码；`@parametrize` 做数据驱动、`fixture` 管依赖生命周期，都是开箱即用。测试圈事实标准 |
| **requests** | Python HTTP 库的事实标准，API 直观。比 urllib 少写一半代码 |
| **PyYAML** | 测试数据用 YAML 比 JSON 好写（能写注释、不用引号）；比 Excel 更好做版本管理（能 diff） |
| **Session 复用连接** | 每条用例新建连接，握手开销大。Session 复用能把整体跑批时间砍掉明显一截 |
| ~~unittest~~ | 断言写法啰嗦（`self.assertEqual`），参数化要自己写循环 |
| ~~Robot Framework~~ | 关键字驱动适合非程序员，但对会 Python 的人反而增加抽象层 |
| ~~Postman + Newman~~ | 适合探索性调试，但复杂逻辑（数据依赖、DB 校验）写起来别扭 |

## 三、目录结构

```
api-framework/
├── config/
│   └── test/
│       └── config.yaml      # 环境配置（base_url / 超时 / 重试）
├── data/
│   └── post_data.yaml       # 测试数据 + 响应结构基线 + 性能基线
├── common/                  # 框架层（用例不该直接改这里）
│   ├── settings.py          # 配置加载、路径管理
│   ├── api_client.py        # HTTP 客户端封装（统一鉴权/超时/日志/重试）
│   ├── validators.py        # 断言工具（失败时带上下文）
│   └── logger.py            # 日志（控制台 info + 文件 debug）
├── testcases/               # 用例层（业务断言都在这里）
│   ├── conftest.py          # fixture：client、数据加载、资源生命周期
│   └── test_posts.py        # 26 条用例（查询/写入/参数化/异常/性能/依赖链）
├── logs/                    # 运行日志（自动创建）
├── reports/                 # 测试报告（后续接 Allure）
└── pytest.ini               # pytest 配置
```

**分层原则**：`testcases/` 只写业务断言，`common/` 负责脏活。
这样加新模块时不必重复写鉴权、超时、日志。

## 四、怎么跑

```bash
# 装依赖
pip install requests pytest PyYAML

# 进目录
cd D:\qa-prep\api-framework

# 跑全部用例
python -m pytest

# 只跑冒烟
python -m pytest -m smoke

# 只跑某个类
```

## 五、用例覆盖了什么

| 分组 | 覆盖内容 | 用例数 |
|---|---|---|
| 查询 | 列表 / 单条 / 带查询参数 / 结构校验 | 4 |
| 写入 | POST / PUT / PATCH / DELETE | 4 |
| 参数化 | 4 组数据 × 创建 + 5 个 id × 查询 | 9 |
| 异常 | 不存在资源 404 / 非法 id / 错误方法 / 缺必填 / 类型错误 | 5 |
| 性能 | 响应时间基线 | 1 |
| 依赖链 | 创建 → 使用 → 清理 | 2 |
| **落库校验** | **接口返回 vs 数据库实际值（含「假成功」识别）** | **6** |
| **合计** | | **31**（28 passed + 3 xfailed） |

### 落库校验（本框架最关键的一环）

只断言状态码和响应体的测试，在「异步写 / 事务回滚 / 主从延迟」这三种情况下都会通过，
但**什么都没验证到**。所以补了 `common/db.py` 做查库对账，并用标准库起了一个真实会写
SQLite 的本地服务（`common/local_api.py`）作为被测对象。

6 条用例覆盖：
- 创建后查库，字段与请求一致
- 创建一条，库里行数必须 +1（防重复写入）
- 打「返回 200 但不写库」的坏端点，证明查库校验能识别假成功
- 查不存在的用户返回 404，且库里确实没有残留
- db 封装自检 2 条（连通性、查不到时返回 None）

> 这条用例同时也是校验机制的哨兵：如果哪天有人把查库那步删了，
> 它会立刻失败，而不是悄悄放行。

## 六、踩坑记录

> 以下是开发过程中实际遇到的问题，记录了现象、排查路径和根因。
> 每一条都可以复现，修复方式已合并进主分支。

### 坑 1：列表接口读超时 —— 回归测试不要请求无上限的列表

**现象**：
```
requests.exceptions.ConnectionError: HTTPSConnectionPool(
    host='jsonplaceholder.typicode.com', port=443): Read timed out.
```

**排查过程**：
一开始怀疑是框架写错了（超时没传进去？requests 版本问题？）。
打印了实际耗时才发现：`/posts` 不带参数时**一次返回 100 条完整文章**，
公网慢的时候光传输就要几十秒。而我的超时设的是 10 秒。

**根因**：接口本身返回体太大 + 公网带宽不可控，不是代码问题。

**修复**：①带上 `_limit=10` 只取 10 条 ②超时放宽到 30 秒

**教训**：
- **回归测试不要请求无上限的列表接口**。真实项目里前端分页，测试也要分页
- 遇到超时先分清"代码写错"还是"环境太慢"，别一上来就怀疑框架

---

### 坑 2：mock 服务不持久化 —— 验证链路前先确认环境行为

**现象**：
我写了「创建文章 → 立刻查询该文章」的依赖链用例，结果：
```
POST /posts        -> 201, 返回 {"id": 101, ...}
GET  /posts/101    -> 404
```

**排查过程**：
先怀疑 id 解析错了 → 打印出来确认是 101；
再怀疑 fixture 顺序问题 → 单独跑还是 404；
最后去查 jsonplaceholder 的文档，才明白：**它是 mock 服务，POST 只是"假装成功"**，
返回一个自增的假 id，资源并没有真的被创建。

**根因**：我把 mock 服务当成了真实服务。

**修复**：把这条用例标成 `@pytest.mark.xfail`，并在注释里写明原因 —— 指向真实接口时去掉标记即可。

**教训**：
- **动手验证链路之前，先确认被测环境是否真的持久化数据**
- 结论是：验证业务链路前，先确认被测环境是否真的持久化数据。否则容易误以为在测业务逻辑，实际是在测 mock 服务的行为。
- `xfail` 的正确用法：**已知的环境限制**标 xfail 并写明原因，而不是删掉用例

---

### 坑 3：YAML 里的类型名是字符串 —— 配置文件驱动的校验都躲不过

**现象**：
在 `data/post_data.yaml` 里写响应结构基线：
```yaml
post_schema:
  userId: int
  id: int
  title: str
```
校验时报：
```
TypeError: isinstance() arg 2 must be a type, a tuple of types, or a union
```

**排查过程**：
打印 `post_schema` 的内容才发现：
```python
{'userId': 'int', 'id': 'int', ...}    # 注意引号！是字符串
```

**根因**：**YAML / JSON 里没有"类型"这个数据类型**。
`int` 被解析成字符串 `"int"`，不是 Python 的 `int` 类。

**修复**：在 `validators.py` 里建一张「名字 → 类型」映射表，
支持配置里写字符串、代码里传真实类型两种方式。

**教训**：
- 凡是**配置文件驱动的功能**（结构校验、字段映射、类型转换）都会遇到这个问题
- 这也是为什么真实项目里更推荐用 `jsonschema` 库 —— 它的 schema 格式本来就是字符串描述的

---

### 坑 4（延伸）：为什么必须加自动重试

**现象**：修完坑 1 之后，用例还是偶发失败。同一条用例这次过、下次挂。

**根因**：**公开 API 本身不稳**。同样的请求，有时 300ms 返回，有时 30 秒不回。

**修复**：在 `api_client.py` 里加了重试机制，但有三个设计要点：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 重试什么 | 只重试**超时 / 连接错误 / 5xx** | 4xx 是客户端错误，重试多少次都一样，只会拖慢 |
| 退避策略 | 1.5s → 3s → 4.5s 递增 | 服务端抖动时，立刻重试往往还是失败 |
| 默认配置化 | `config.yaml` 里 `retries: 2` | 内网接口不需要重试，走公网才需要 |

**教训**：
> **「被测服务是稳定的」是测试的假设，不是事实。**
> 对不稳定的外部依赖，要么加重试，要么明确标记为不稳定用例。

## 七、已知不足

目前明确的短板有四处：

1. **测试数据隔离不够** —— 落库校验用的是本地 SQLite，同一个库反复跑。
   真实项目要多环境隔离 + 用例级唯一数据（或用后即删），否则并发跑会互相干扰
2. **CI 覆盖不全** —— GitHub Actions 已接（push 自动跑），但只做了测试执行与产物上传，
   还没接报告发布（Pages）和失败通知；Jenkins 侧未验证
3. **结构校验太简单** —— 手写的 `assert_schema` 不支持嵌套、枚举、正则，真实项目该用 jsonschema
4. **落库校验只覆盖 SQLite** —— 真实项目要换成 pymysql，并处理连接池、主从延迟

> 这四条也是下一版的优先级依据。
