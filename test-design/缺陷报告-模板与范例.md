## 一、缺陷报告模板

> 复制这张表直接填。六要素齐了才算合格——缺一条，开发就得回来问你要。

| 字段 | 填写要求 | 示例 |
|---|---|---|
| **缺陷标题** | 在哪 + 什么操作 + 什么现象，一句话 | 微信退出登录后，仍能收到新消息推送 |
| **所属模块** | 功能模块名 | 消息推送 |
| **环境** | 机型 / 系统版本 / App 版本 | realme GT8 · Android 16 · 微信（最新正式版） |
| **前置条件** | 复现前必须满足的状态 | 已登录，且已开启消息通知权限 |
| **复现步骤** | 编号列出，至少 3 步，要能被别人照着重现 | 1. 登录账号 A<br>2. 进入设置 → 退出登录<br>3. 用另一台设备给 A 发消息 |
| **预期结果** | 应该发生什么，必须可验证 | 退出后不再收到任何新消息 |
| **实际结果** | 实际看到了什么 | 仍能收到消息并弹出通知横幅 |
| **严重程度 Severity** | 致命 / 严重 / 一般 / 轻微（按技术影响） | 一般 |
| **优先级 Priority** | 高 / 中 / 低（按业务影响） | 中 |
| **影响范围** | 影响多少用户、哪些功能、有无数据或资金风险 | 所有 Android 用户，旧设备仍可收消息，存在隐私泄露 |
| **初步定位建议** | 猜是哪一层的问题，给开发一个方向 | 退出登录时未注销推送 token |
| **建议修复方案** | 给修复方向，不是替开发写代码 | ① logout 注销设备 token ② 使旧 token 失效 ③ 推送前校验设备状态 |
| **附件** | 截图 / 录屏 / 日志片段 | 录屏 1 段（12 秒） |

**两条硬要求：**

1. **标题要能被搜到**——「登录有问题」搜不出来，「未注册手机号提示"密码错误"」一搜就到。
2. **步骤要能被别人重现**——你自己照着重走一遍，能看到同样的现象，才算写完。

## 二、合格缺陷报告的六要素

| 要素 | 说明 | 常见错误 |
|---|---|---|
| **1 标题** | 一句话说清"什么条件下、什么模块、出了什么错" | 只写"登录有bug"，等于没说 |
| **2 环境** | 设备型号 / 系统版本 / App 版本 / 网络 | 漏了就无法复现 |
| **3 前置条件** | 复现前必须处于什么状态（已登录？哪个账号？） | 写"打开App"这种废话 |
| **4 复现步骤** | **编号、可照做、每步只有一个动作** | 把多步挤在一句话里 |
| **5 预期结果** | 按需求应该是什么 | 和实际结果写成一样的话 |
| **6 实际结果** | 真实观察到的现象（**附截图/日志**） | 只写"不对"、"有问题" |

**加分项**：复现概率（偶现 3/10）、严重程度 vs 优先级、定位建议、附件

## 三、Severity（严重程度）vs Priority（优先级）

**这两个概念容易混淆，很多人答反。**

| | Severity 严重程度 | Priority 优先级 |
|---|---|---|
| 谁定 | **测试**（看技术影响） | **产品/项目经理**（看商业价值） |
| 看什么 | 功能坏得多厉害、影响多少用户 | 先修哪个、能不能拖着 |
| 例子 | 崩溃、数据丢失 = 高 | 首页错别字 = 低 |

**两个典型反例**（说明两者为什么不能划等号）：

| 场景 | Severity | Priority | 为什么 |
|---|---|---|---|
| **首页公司 logo 放错** | 低（不影响功能） | **高**（老板一眼看到，影响品牌） | 技术影响小，商业影响大 |
| **闰年 2 月 29 日签到失败** | **高**（功能完全不可用） | 低（一年就一次，可以先排后面） | 技术影响大，发生频率极低 |

## 四、范例 1：微信「退出登录后仍能收到消息」

```
【标题】
Android 微信退出登录后，仍能收到消息推送，点击通知直接进入聊天页

【环境】
设备：realme GT8 / Android 16 / realme UI 7.0
App：微信（最新正式版）
网络：WiFi 5G
执行日期：2026-03-18
复现概率：10/10（必现）

【前置条件】
1. 账号 A 已登录
2. 系统已授予微信通知权限
3. 已开启"新消息通知"

【复现步骤】
1. 打开微信，进入「我 → 设置 → 退出登录」
2. 确认退出，回到登录页
3. 用另一台设备登录账号 A，向账号 A 发送一条消息
4. 观察已退出的这台设备的通知栏
5. 点击收到的通知

【预期结果】
步骤 4：退出登录后不应再收到任何消息推送
步骤 5：无通知可点

【实际结果】
步骤 4：通知栏出现"张三：在吗"，并伴随提示音
步骤 5：点击通知，App 直接打开到与张三的聊天页（未要求重新登录）

【影响范围】
- 受影响用户：所有在 Android 端执行「退出登录」的用户，无需特殊环境
- 受影响设备：仅限退出登录的那台旧设备；同账号在新设备登录不受影响
- 影响功能：消息推送、会话管理、隐私安全
- 数据影响：旧设备可继续接收并查看新消息，**会话 token 未失效**
- 风险等级：隐私泄露。手机上已退出登录，但内容和通知仍对持机人可见
- 复现概率：10/10（必现，无需构造条件）

【严重程度】高（S2）
理由：退出登录的核心语义是"切断该设备与账号的关联"，
      能收到消息意味着会话未真正失效，属隐私泄露风险

【优先级】高（P1）
理由：涉及用户隐私，且新设备登录后旧设备仍在线，用户投诉风险高

【定位建议】
怀疑退出登录时未断开 push 长连接 / 未在服务端注销该设备 token，
建议检查 logout 接口是否调用设备注销逻辑。

【建议修复方案】
1. **服务端**：logout 接口增加"注销该设备 push token"逻辑，把 device_id 从推送名单中移除
2. **服务端**：使该设备的登录 token 立即失效（加入黑名单或缩短有效期）
3. **客户端**：退出登录后主动断开 /sync 长连接，清空本地缓存的会话信息
4. **兜底**：推送服务在下发前校验设备状态，已退出设备直接丢弃（避免依赖客户端自觉）
5. **验证方式**：退出后用服务端工具强制推送一条测试消息，确认旧设备无任何提示音与横幅
6. **回归范围**：多端登录、切换账号、卸载重装、退出后重新登录
```

**这个 bug 的价值**：它体现你**理解"退出登录"的语义边界**，而不是只看"点一下有没有回登录页"。
把范围收窄到具体链路，比笼统描述"按钮点不动"更有定位价值。

## 五、范例 2：淘宝「提交订单成功但订单列表查不到」

```
【标题】
淘宝 App 弱网下提交订单返回成功，但订单列表无该订单，重进后订单出现

【环境】
设备：realme GT8 / Android 16 / realme UI 7.0
App：淘宝（最新正式版）
网络：地铁 4G，信号 2 格（用 Charles 限速 100KB/s + 800ms 延迟模拟）
执行日期：2026-03-25
复现概率：3/10（弱网下偶现）

【前置条件】
1. 已登录
2. 购物车中有 1 件商品
3. 已设置默认收货地址和支付方式

【复现步骤】
1. 用 Charles 把网速限到 100KB/s、延迟 800ms
2. 进入购物车 → 全选 → 结算
3. 确认订单 → 点击「提交订单」
4. 观察提交结果提示
5. 提交后立即进入「我的 → 我的订单 → 全部」
6. 下拉刷新订单列表
7. 杀掉 App 重新打开，再次查看订单列表

【预期结果】
步骤 4：提示"提交成功"
步骤 5-6：订单列表中应能立即看到该订单
步骤 7：订单仍存在

【实际结果】
步骤 4：提示"提交成功"，页面跳转到支付页
步骤 5-6：订单列表为空，下拉刷新后仍为空
步骤 7：重新打开后订单正常出现在列表中
     → 说明订单**已落库**，问题在步骤 5-6 的列表数据未同步

【影响范围】
- 受影响用户：弱网环境下的下单用户（地铁、电梯、地下车库、高铁等场景）
- 影响功能：订单列表、支付流程、售后凭证
- 触发条件：网络延迟 ≥ 800ms 时约 3/10 概率，网络越好越难复现
- 数据影响：订单**已落库，不会丢单**，纯粹是列表读取链路的问题
- 业务风险：用户误以为下单失败 → 重复提交 → **重复订单 / 重复支付**
- 次生影响：用户找客服时，"我明明下单了但看不到"这类工单很难自证

【严重程度】高（S2）
理由：用户会误以为下单失败而重复提交，可能导致重复订单/重复支付

【优先级】高（P1）
理由：涉及资金，且弱网是真实高频场景

【定位建议】
疑似订单列表接口读取了从库/缓存，而订单创建写主库，
存在主从同步延迟。建议确认 /order/list 是否走缓存、TTL 多长。

【建议修复方案】
1. **读己之写**：订单创建后的一段时间内（如 30 秒），该用户的列表查询强制走主库
2. **本地兜底**：提交成功后把 orderId 写入本地"待确认订单"，列表页优先合并展示
3. **缓存失效**：订单创建成功时主动删除该用户的订单列表缓存，而不是等 TTL 自然过期
4. **交互优化**：跳转支付页时提示"订单处理中，可在「我的订单」查看"，降低用户立刻返回核对的概率
5. **长期方案**：订单创建事件通过消息队列同步到列表服务，保证最终一致并缩短延迟窗口
6. **验证方式**：用 Charles 限速 100KB/s + 800ms 延迟复现，确认列表在 1 秒内可见该订单
7. **回归范围**：正常网络下单、弱网下单、并发下单、取消订单后列表同步
```

**这个 bug 的价值**：它展示了**测试的核心能力——定位而非描述**。
你没有停在"订单看不到"，而是用"重开就有"排除掉"订单没落库"，
把范围收窄到"列表读取链路"。**这是排查时应该走的顺序：先缩小范围，再定位。**
