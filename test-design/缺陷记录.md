## 二、缺陷分级标准

本项目采用四级严重程度、三级优先级，两者独立评定。

**严重程度（Severity）**：按技术影响划分。

| 级别 | 定义 |
|---|---|
| S1 致命 | 崩溃、数据丢失、核心链路完全不可用 |
| S2 严重 | 主要功能异常或存在合规 / 安全风险，但有可用路径 |
| S3 一般 | 次要功能异常、提示文案错误、局部体验问题 |
| S4 轻微 | 界面细节、不影响使用的显示问题 |

**优先级（Priority）**：按业务影响与修复紧迫性划分。

| 级别 | 定义 |
|---|---|
| P1 高 | 影响合规、资金、隐私，或大面积用户，需在当前版本修复 |
| P2 中 | 影响部分用户或特定场景，可排入近期版本 |
| P3 低 | 影响面小、发生频率低，可延后处理 |

两者不构成线性对应关系。例如首页品牌标识错误属于 S4 严重程度、P1 优先级；闰年 2 月 29 日签到失败属于 S2 严重程度、P3 优先级。

## 三、缺陷详情

### DEF-2026-001　未勾选《用户协议》时仍可完成登录

| 字段 | 内容 |
|---|---|
| **所属模块** | 登录 · 协议勾选 |
| **发现方式** | 界面走查 + 用例 TC-F01（安全与状态 / 协议校验） |
| **环境** | realme GT8 · Android 16 · realme UI 7.0 · 微信最新正式版 · WiFi 5G |
| **复现概率** | 10/10（必现） |
| **前置条件** | 已进入登录页；手机号与密码均为合法值；账号处于未登录状态 |

**复现步骤**

1. 打开微信，进入登录页。
2. 输入已注册手机号与正确密码。
3. 不勾选页面底部的《用户协议》与《隐私政策》。
4. 点击「登录」按钮。
5. 观察页面跳转与登录结果。

**预期结果**

- 未勾选协议时，「登录」按钮应处于禁用态；或点击后提示「请先阅读并同意《用户协议》和《隐私政策》」，且不发起登录请求。
- 登录成功后，服务端应记录用户同意的协议版本与时间。

**实际结果**

- 步骤 4：按钮为可点击态，点击后正常发起登录请求。
- 步骤 5：登录成功并进入首页，全程未出现协议确认提示。
- 抓包确认：登录请求体中不含 `agree_version`、`agree_time` 等协议同意字段。

**影响范围**

- 受影响用户：所有首次登录或协议更新后登录的用户。
- 影响功能：登录流程、用户协议合规链路。
- 数据影响：服务端无协议同意记录，无法举证用户已同意。
- 风险：违反个人信息处理「告知—同意」要求，存在合规与审核风险。

**严重程度**：S2 严重。理由：不导致功能不可用，但直接构成合规缺口，且涉及全部新用户。

**优先级**：P1 高。理由：合规问题通常为版本上线的阻断项。

**定位建议**

- 客户端：「登录」按钮的 `disabled` 条件未纳入协议勾选状态，仅校验了手机号与密码是否为空。
- 服务端：登录接口未将协议同意版本作为必填参数校验，因此客户端即使传空也能通过。

**修复建议**

1. 客户端将按钮可用状态绑定为「手机号合法 && 密码非空 && 已勾选协议」。
2. 登录接口增加 `agree_version`、`agree_time` 必填校验，缺失时返回参数错误。
3. 服务端持久化同意记录，支持按用户与版本查询，用于合规举证。
4. 协议版本更新后，登录时重新征得同意，并记录新版本。

**验证标准**

- 不勾选协议点击登录：无网络请求发出（抓包验证），页面提示协议确认。
- 勾选后登录：请求体包含协议版本与时间，服务端可查到对应记录。
- 协议版本升级后登录：强制弹出协议确认，确认前无法登录。

**状态**：已复现，缺陷单已记录，待修复验证。

### DEF-2026-002　未注册手机号返回差异化提示，可用于账号枚举

| 字段 | 内容 |
|---|---|
| **所属模块** | 登录 · 账号校验 |
| **发现方式** | 用例推演（TC-F02 防撞库枚举）+ 接口返回对比 |
| **环境** | realme GT8 · Android 16 · realme UI 7.0 · 微信最新正式版 · WiFi 5G |
| **复现概率** | 10/10（必现） |
| **前置条件** | 已进入登录页；准备一个未注册手机号与一个已注册手机号 |

**复现步骤**

1. 输入**未注册**手机号，密码随意填写，点击登录。
2. 记录返回的提示文案与错误码。
3. 输入**已注册**手机号，密码故意填错，点击登录。
4. 记录返回的提示文案与错误码。
5. 对比两次返回的差异。
6. 连续 10 次提交未注册手机号，观察是否触发频率限制或验证码。

**预期结果**

- 两类失败的提示文案与错误码保持一致（如统一为「账号或密码错误」）。
- 同一设备或 IP 连续失败达到阈值后，触发图形验证码或短信验证码。
- 服务端对枚举行为有监控与告警。

**实际结果**

- 步骤 2：未注册号码返回「该手机号未注册」，错误码与「密码错误」不同。
- 步骤 4：已注册号码返回「密码错误」。
- 步骤 5：两类提示可直接区分号码是否已注册。
- 步骤 6：连续 10 次提交未注册号码，未触发验证码或限流。

**影响范围**

- 受影响用户：全部用户。
- 影响功能：登录校验、注册引导、账号安全。
- 数据影响：无直接数据泄露，但可获得「某手机号是否为平台用户」的确定结论。
- 风险：可被用于批量账号枚举，进而支撑撞库、精准营销骚扰、诈骗话术准备。

**严重程度**：S2 严重。理由：不直接影响功能可用性，但为账号安全链路提供可利用的信息差。

**优先级**：P1 高。理由：枚举成本极低，且与撞库风险直接相关，属安全基线问题。

**定位建议**

- 服务端在账号不存在时返回了独立的错误码（如 1001）与文案，前端直接透传。
- 登录接口缺少针对「同一手机号 / 同一设备 / 同一 IP」的失败计数与限流策略。

**修复建议**

1. 统一登录失败的文案与错误码，不区分「账号不存在」与「密码错误」。
2. 引入失败计数：同一手机号连续失败 5 次、同一设备连续失败 10 次触发图形或短信验证码。
3. 注册与找回密码流程同步排查：避免「该号码已注册」这类直接暴露状态的提示。
4. 服务端增加枚举行为监控（短时间大量不同号码的失败请求）并告警。
5. 对已登录用户提供登录设备管理，便于用户自查异常登录。

**验证标准**

- 两类失败返回完全一致的 code 与文案。
- 连续失败达到阈值后强制验证码，且验证码不可绕过。
- 监控面板可查询到异常枚举请求的记录。

**状态**：已复现，缺陷单已记录，待修复验证。
